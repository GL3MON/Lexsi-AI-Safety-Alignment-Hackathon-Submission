# Retail training data plan

The local Tau2 retail dataset has 114 task scenarios: 74 in the official training split and 40 in the official test split. A task can produce multiple conversations; these counts do not describe an existing corpus of complete SFT conversations.

Generate and freeze the partition manifest:

```bash
.venv/bin/python scripts/prepare_retail_splits.py
```

The script refuses to replace an existing manifest. Use `--output` for an alternative manifest and keep the chosen file fixed throughout an experiment. Counts and seed are configurable.

| Partition | Tasks | Purpose |
|---|---:|---|
| SFT | 40 | Generate 3–5 accepted demonstrations per task: 120–200 complete conversations |
| RL | 22 | Sample 4–8 fresh rollouts per task per sweep: 88–176 rollouts |
| Validation | 10 | Select checkpoints and settings; exclude from training |
| Official test | 40 | Final evaluation; preserve the official task IDs |
| Review | 2 | Training tasks 4 and 7 have open issue annotations |

The manifest is `outputs/retail-data/split_manifest.json`. It records source-data SHA256, all task IDs, open issue details, and the conversation/rollout quotas. Partitions are disjoint by task ID. They do not guarantee disjoint customers or orders. Tasks already used in exploratory retail previews are kept out of the new validation partition.

For SFT, use a capable teacher and customer simulator. Retain complete multi-turn conversations with clarification questions, authentication, grounded arguments, real tool results, and policy-correct completion. Require actual Tau2 success and inspect policy adherence: the database reward alone does not enforce every policy rule. Reject malformed calls, invented identifiers, agent-like customer replies, and fabricated success claims. A conversation is one sample; its assistant turns supply multiple supervised targets. Mask customer/tool observations from the loss, retaining the established tool-response format.

For RL, initialize from retail SFT and execute fresh trajectories on the RL task IDs. Repeated rollouts are samples of the same task, not extra independent tasks. Track per-task variance and failure types. If all rollout rewards are zero, address the policy or simulator/data issues before spending a long run on GRPO. Save the user model identity with each run and keep it fixed for comparisons.

Task reference actions and evaluation checks are available to offline data generation and validation, but must not be put into the policy's inference prompt. No demonstrations or RL trajectories are generated by the split script itself.

## Prepared endpoints and SFT configuration

The chosen generation model is the untouched `CohereLabs/tiny-aya-global`, pinned at `af89d219b53ed9b13b8a4645f9c8028973510324`, for both teacher-agent and customer roles with separate conversation contexts. Start its original-template server with `scripts/serve_retail_user.sh`; it serves `tiny-aya-base-user` at `http://127.0.0.1:8003/v1` on MIG2. Settings are recorded in `configs/retail-generation.json`. Endpoint availability does not imply that its generated conversations are correct; success and policy checks remain necessary.

`configs/sft-retail.json` starts from the merged function-calling checkpoint 525, uses AgentTune, W&B online, batch size 1 with accumulation 8, and requires:

- `outputs/retail-data/sft.jsonl`: accepted conversations with `task_id` in the SFT partition.
- `outputs/retail-data/validation.jsonl`: conversations with `task_id` in the validation partition.

Each JSONL record must include `messages` and `task_id`. System messages must contain the retail policy and tool schemas inside `<tools>` tags. Assistant calls use `<tool_call>{"name": ..., "arguments": ...}</tool_call>`. Structured tool observations with a name are normalized to the tagged user turns used by Aya during SFT; their labels are masked.

The trainer checks explicit task reservations before tokenization and records evaluation-file and split-manifest hashes. It does not select validation conversations out of the SFT tasks when an explicit validation file is configured.

Once both verified datasets exist, stop the base-user server on MIG2 to release memory before training:

```bash
scripts/run_retail_sft.sh --prepare-only
scripts/run_retail_sft.sh
```

The prepare-only command verifies actual token lengths and assistant-label masks. Long retail conversations may exceed the 8192-token context; preparation currently fails rather than silently truncating policy, observations, or supervision. Such conversations require valid bounded-context examples before training. No ready-to-train retail conversation files have been generated yet.
